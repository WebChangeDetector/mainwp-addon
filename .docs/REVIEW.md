# MainWP Add-on Review Conventions

Rules for implementing and reviewing the WebChange Detector MainWP add-on. Architecture, data flow, the safe-update pipeline, setup and troubleshooting: see `MAINWP.md`. Hook/filter details and the two guarded internal calls: see `MAINWP-HOOKS.md`.

## Paths & deployment boundary

- **NEVER edit** `/Users/mike/htdocs/wcd/wp-repo-mainwp/`: it is the generated wordpress.org distribution, produced by `scripts/build-release.sh` (rsync minus `.distignore`). Any change there is overwritten on the next build.

## Integration principle

- Integrate through **documented MainWP hooks/filters only**. The only exceptions are the two operations with no hook (fetch a child site's pages; trigger a single site's update), which use `class_exists`/`method_exists`-guarded internal calls and must degrade to a notice (never a fatal) if MainWP changes them. Do not add new internal MainWP calls without the same guarding and a note in `MAINWP-HOOKS.md`.
- No WCD API call before a token is configured (wordpress.org guideline 7). Guard every API path on `WCD_MainWP_Site_Settings::get_global()` being non-empty.

## Naming

- Slug, folder, main file and text domain are all **`webchangedetector-for-mainwp`** ("X for MainWP" naming; a slug starting with `mainwp` violates trademark guideline 17). Never rename to start with `mainwp`.
- PHP: WordPress coding standards, classes `WCD_MainWP_*`, methods snake_case, constants UPPER_SNAKE_CASE.
- Local template variables echoed in templates carry a `wcd_mainwp_` prefix (avoids clashing with MainWP's own template scope).

## Mandatory Patterns

- **All user-facing copy** through `__()`/`esc_html__()`/`esc_attr__()`/`wp_kses_post()` with text domain `webchangedetector-for-mainwp`. No bare strings in markup.
- **Escape on output**: `esc_html`, `esc_attr`, `esc_url`; `wp_kses_post` only for strings that intentionally contain links/markup (e.g. `WCD_MainWP_Bootstrap::no_token_hint_html()`).
- **External CSS/JS only.** Styles live in `assets/css/`, scripts in `assets/js/`; never inline `<style>`/`<script>` or `style=`/`on*=` attributes. Use existing CSS custom properties (e.g. `--wcd-muted`) and Semantic/Fomantic UI classes already in the markup.
- **Strings to JS** go through `WCD_MainWP_Bootstrap::js_strings()` + `wp_localize_script`, read via the `t()` helper in `wcd-mainwp.js`. Do not hardcode copy in the JS file.
- **One extension page, four tabs.** The whole UI (Run / Checks / Settings / Account) lives on the add-on's extension page (`templates/admin-page.php` shell), switched by a `?tab=` full-page reload. Always build tab URLs with `WCD_MainWP_Bootstrap::tab_url($tab)` (never hand-assemble `?page=...&tab=...`, never reintroduce `ManageSites*` Sites subpages for these or a left-menu/Monitoring entry). The switcher (`render_tabs()`) is MainWP's native sub-navigation bar rendered as a Fomantic `ui labeled icon inverted menu mainwp-sub-submenu` (the same classes the SeoPress add-on uses; icon over label). The `inverted` class is mandatory: the theme scopes the white labels/icons and the active-tab highlight to `.ui.inverted.menu.mainwp-sub-submenu` (bare `.mainwp-sub-submenu` is dark-background only, so without `inverted` the labels are unreadable and the active tab is invisible). Add NO custom tab CSS (`labeled icon` stacks icon-over-label natively; custom rules fight the theme) and never re-introduce a `top attached tabular menu`. Tab body templates are chrome-less: the shell renders `mainwp_pageheader_extensions` + `render_tabs()`; because the native bar is free-standing, bodies start at a plain `ui padded segment` (not `bottom attached`). Reading the active tab from the request uses `filter_input(INPUT_GET, 'tab', ...)` + `sanitize_key()` + an explicit whitelist (display-only navigation, so no nonce and no `$_GET` superglobal access that would trip phpcs). The only remaining Sites subpage is the per-site `WcdVisualRegressionTesting` tab.
- **AJAX handlers** (`WCD_MainWP_Ajax`) verify the nonce (`check_ajax_referer`) AND `current_user_can('manage_options')` via `self::verify()` before any work. Sanitize every `$_POST` field.
- **Browser is the scheduler.** Operations that fan out over many sites (bulk sync, the safe-update pipeline) iterate **one site per AJAX request from JS**, not a server-side loop over all sites. A single request must never stack many slow WCD API calls (PHP timeout + credit-burn risk). Reuse existing per-site endpoints (`toggle_site`, `sync_urls`) rather than adding bulk server endpoints.
- **Safe-update run popup + resume.** The live run card is mounted into the shared Fomantic modal (`mountRun`), NOT inline in the page. While a run is in flight the popup cannot be closed: `mayCloseModal` returns `!activeRun` to veto the close and a keep-open warning is shown. The native Fomantic close icon is hidden in the run popup at all times (CSS on `.wcd-run-modal`); the card's OWN dismiss (`.wcd-run__dismiss`) is the single close affordance and only appears once the run finishes (`data-state` done/error), so there is never a duplicate close. The modal's `onHidden` must NOT clear content while a run card owns it (`activeRunRef` guard). A **fresh** run opens the popup immediately (`mountRun(..., true)`); a **resumed** run does NOT auto-open (`mountRun(..., false)`), so the only way in is the **"Updates running" reopen button** rendered into `.wcd-run-reopen-slot` (widget header) or, as a fallback, the `.wcd-run-host` (banner). Because the browser drives the phases, every transition is persisted in `wcd_mainwp_active_run` and the driving tab sends an unthrottled `run_heartbeat` carrying a per-tab **driver id** (`sessionStorage`); `checkResume` takes over **instantly** when the run's `driver` matches this tab (a same-tab reload reclaiming its own run) or when the heartbeat has been silent for `RESUME_AFTER`, else it shows the "Updates running" button + locks the CTA immediately and re-checks after `RESUME_RECHECK` (the two-tab guard: never auto-drive a run another tab is still heartbeating). Resume must stay **credit-safe**: re-take only the still-missing PRE screenshots and update only the not-yet-updated sites (never re-shoot/re-update what the persisted state already recorded). Dynamic widths (timeline fill) use the `.wcd-w-*` step utilities, never inline styles.
- **Cost transparency.** Enabling/activating a site provisions WCD websites and groups (billing is per check; websites are unlimited on every plan). Never enable/activate sites silently or in bulk without explicit user action (the per-site toggle, or a `window.confirm` before "Activate checks for all websites"). User-facing copy frames this as *activating visual checks*, never as *syncing* (the URL sync runs in the background; show a spinner and raise the `beforeunload` guard while it runs).
- **Account-bound provisioning.** The site map (`wcd_site_map`) stores website/group UUIDs that only resolve for the account behind the current API token. When the token changes, the stored UUIDs belong to the previous account and every group call 404s. So: on a token change in `handle_save_settings()`, call `WCD_MainWP_Site_Map::reset_all()`; and when a group call returns HTTP 404, self-heal with `WCD_MainWP_Site_Map::reset_site()` and surface a "re-sync this site" message instead of the raw API error (see `WCD_MainWP_Ajax::reject_if_group_gone()`). Never trust stored UUIDs across an account switch. The explicit Account-tab "Reset connection" button (`reset_connection()`) is the user-driven version: it is **local only** (clears token + site map + caches + any in-flight run via `clear_run()`), never deletes WCD-side data, and stays idempotent on reconnect via `find_existing_website()`.
- **Separate website per integration (`managed_by`).** MainWP websites carry `managed_by=mainwp` on the API so their `?p=ID` URLs never mix with the first-party clean permalinks (the API keeps one website per `(user, domain, managed_by)`). Always send `managed_by` (`WCD_MainWP_API::MANAGED_BY`) when creating a website, and the `x-wcd-managed-by` header on every sync call (`sync_urls`/`start_url_sync`). Before creating a website, look it up first (`get_websites()` + `find_existing_website()`): if the account already has the MainWP website for that domain, re-link to its UUIDs instead of provisioning duplicates (this, with the account reset above, makes token switching idempotent).
- **Per-site On-Demand settings (incl. screenshot region).** Each enabled site has a **Settings** button on the Settings tab that opens the per-site **On-Demand check settings modal** (`templates/site-settings-modal.php`, one server-rendered Fomantic `ui modal` reused for every site; the JS fills its values on open). The modal reads via the `get_site_settings` AJAX action (`GET /groups/{id}` on the manual group) and writes via `save_site_settings`. Capture settings go to the **manual** group via `update_group`; `screenshot_region` is written to **both** groups (manual + auto) and persisted via `WCD_MainWP_Site_Map::set_region()`. The API owns sibling-sync + resolving `auto` to a concrete region, so never loop or poll for resolution here. The valid region set + sanitizer live in ONE place (`WCD_MainWP_Site_Map::REGIONS` / `::sanitize_region()`); reuse them everywhere (AJAX, provision) rather than re-listing `['us','eu','auto']`. Per-field save contract (the API writes a field only when present in the request): `proxy_type` is `static`/`none` (never `''`); `screenshot_delay` is clamped 7 to 60 or the key is omitted when empty; `basic_auth_password` is **sent to set, `''` to clear, omitted to leave unchanged** (there is NO `basic_auth_password_action` field on the API); the password is never returned, so use the `has_basic_auth` flag for the "password is stored" state; `css`/`js` are stored verbatim (only unslashed, not sanitized, matching the API/webapp). The group fields the add-on may send live in ONE allow-list, `WCD_MainWP_API::GROUP_FIELDS`, shared by `create_group`/`update_group` (`array_intersect_key`): any new group field must be added there or it is silently dropped. (Removed: the inline per-site region dropdown, the `set_region` AJAX action, and `WCD_MainWP_Site_Map::resolved_regions()` page-load prefill, all superseded by the modal.)
- **No native heartbeat for MainWP websites.** Because the add-on sends `x-wcd-managed-by=mainwp` and omits `x-wcd-plugin`, the API's `SetLastSeenAt` deliberately does NOT set `last_seen_at`/`plugin_version` on a MainWP website (those are the native WP-plugin heartbeat). MainWP-managed websites therefore have a null `last_seen_at` by design — do not treat it as "offline"; the webapp shows them with the "MainWP" managed-by badge, not a plugin-status badge.

## Text rules

- **Never use double-hyphens or em-dashes** in any copy, comment, or doc. Use commas, colons, semicolons, or restructure.
- English only for code, comments, and docs.

## Backward compatibility

- AJAX endpoints accept both the legacy single-value shape (`site_id`, `batch`) and the newer array shape (`site_ids[]`, `batches[]`); keep both when touching a handler.
- Additive response fields only; do not remove or rename existing keys consumers (the JS) read.

## Deprecated / Forbidden

- No edits to the `wp-repo-mainwp` deployment folder (see Paths).
- No AI model names or internal crop URLs in any user-facing surface (the API strips these server-side; keep them out of templates/JS too).
- No new dependency on undocumented MainWP internals without a guarded fallback.
